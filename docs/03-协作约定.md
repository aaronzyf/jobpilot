> 整理日期：2026-11-28

> 适用对象：任何接手本仓库的开发者或 AI 助手
> 配套：`docs/01-需求与架构方案.md`（设计与意图）、`docs/02-项目交接文档.md`（项目现状与接手须知）

## 零、这份文档的定位

前面两份文档讲的是「这个软件是什么、现在做到哪」。这份文档讲的是「**在这个项目里应该怎么干活**」——它记录的是需求之外的协作方式与工程纪律，来自实际开发过程中提出并已落地的要求。

**优先级**：本文件与架构文档冲突时，以本文件为准（它记录的是需求方的直接要求，架构文档是技术推导）。

## 一、沟通与节奏

### 1.1 需求阶段：先听全，别抢跑

> 原话：「先不要开始做」「你先别做方案，你只先听我的需求，等我说完了，我们再一起生成方案」

需求还在口述阶段时，**不要急着写代码或出方案**。先完整接收、记录、归类，等明确信号（「好，我们来出一个方案」）再动手。一次给一份完整方案，而不是边听边做。

### 1.2 任务可以自行拆解，但拆完就各自提交

> 原话：「我给你布置的任务，你可以自己拆分，拆分出来的小任务每一步你都要提交」

接到一个较大的任务时，**主动拆成若干可独立验证的小任务**，然后按顺序执行。拆解过程不需要反复确认——自己拆、自己做、自己验。

### 1.3 短指令驱动，靠上下文接续

> 原话（多次）：「继续」「请继续完成未完成的任务」「好的 按你说的来」

用户会用极短的指令推进，这意味着**你必须自己记住上下文并接续**。不要反问「您是指哪一项」，也不要把上一次已经确认过的结论再问一遍。做不到的事要明说并给出替代方案，而不是含糊带过。

### 1.4 遇到方向性歧义时给选项，并说明倾向

> 原话：「加号应该换个图标，应该让人感知点了之后是到列表，或者直接换成"管理"两个字」

用户给出多个可选方向时，**列出选项并表明推荐项与理由**，然后按推荐执行；用户没反对就继续。不要罗列一堆可能性却不落地。

## 二、代码组织

### 2.1 分层铁律

> 原话：「代码做好分层 比如数据读取那一层 Service 业务层 然后从 UI 层一层一级一级地去调用」

**数据读取层 → Service 业务层 → UI 层，逐级调用，不许跨级。**

| 层 | 位置 | 只做 | 不做 |
|---|---|---|---|
| Repository | `main/db/repositories/` | 单条 SQL，返回数据库行 | 业务规则、组装 View、决定版本号 |
| Mapper | `main/db/mappers/` | 行 → View 的纯函数 | 查库、写库 |
| Service | `main/db/services/` | 用例编排、决定取哪几组数据 | 写 SQL |
| IPC 契约 | `packages/core/src/ipc/contract.ts` | 通道名 → 参数 → 返回 | — |
| preload | `preload/index.ts` | 只暴露 `invoke` / `send` / `on` | 认识任何业务通道 |
| renderer service | `renderer/src/services/` | 把 IPC 包成业务函数 | 直接拼通道名 |
| UI | `renderer/src/pages/`、`components/` | 消费 store 的字段 | 直接调 ipc（设置页取 `app:info` 除外） |

新增功能时按这个顺序铺：先加领域类型 → 再加仓储 → 再加 mapper → 再加 service → 再加 IPC 契约 → 再加 renderer service → 最后加 UI。**不要从 UI 层倒着写。**

### 2.2 业务与 UI 分离，数据归主进程

> 原话：「我希望业务和 UI 逻辑分离，也就是说如果我关掉了 UI 进程，那么数据应该是还在的。渲染进程通过进程通信把数据传过去。写一个统一的进程通讯函数入口」

- **SQLite 连接只在主进程持有**，渲染层永远不碰数据库。
- **写一个统一的进程通讯函数入口**（`main/ipc/registry.ts` + `packages/core/src/ipc/contract.ts`），所有跨进程调用都从这里过，不允许在业务文件里直接出现裸 `ipcMain`。
- 后台任务（匹配调度等）只活在主进程：窗口关掉、切页、换筛选都不影响它。

### 2.3 按页读取，不做一次性全量快照

> 原话：「不要做一次性拉取 虽然可以自行拉取 但是进到对应的页面还是要重新读的」

进入页面必须重新查库，不能用启动时拉的全量快照糊弄。筛选条件要**下推到 SQL**，不是在内存里过滤。

### 2.4 接口隔离，不是"大接口"

> 原话：「我说用 interface 是一种设计模式啊，它不是说把所有的都塞到同一个 interface 里面，你根据不同的需要去拆分」

按能力拆成小接口，用组合拼装（`JobSource` = `meta` + `auth` + 可选的 `list`/`detail`/`apply` + 必填 `normalizer`）。**没实现的能力要在类型层面就不成立**，而不是留个 `throw new Error('not implemented')` 的空壳。

### 2.5 数据结构先行

> 原话：「好 开始设计数据结构吧 并且把表结构建出来 数据操作使用 ORM 并且往数据库里面塞一些测试数据，把现在模拟数据塞到数据库里并且改用。从数据库中读取的方式」

- 表结构用 **Drizzle ORM** 定义，迁移用 `drizzle-kit` 生成 SQL。
- **不要长期依赖 mock 数据**。数据源应尽快换成真实数据库；示例数据是灌进 SQLite 的种子，不是内存假数据。
- 种子时间按「相对此刻」生成，不写死中文日期字符串。

### 2.6 模块化组织，不要单文件堆砌

偏好合理的目录结构而非单文件堆砌（单个文件超过 ~500 行就该拆）。新增组件放 `components/<模块>/`，新增数据访问放对应的 `repositories/`。

## 三、Git 与提交

### 3.1 每完成一个小任务就提交

> 原话：「我给你布置的任务，你可以自己拆分，拆分出来的小任务每一步你都要提交」

- **拆出的每个小任务完成后单独提交**，不要把不相关的改动混进一个 commit。
- 一次提交对应一个可独立验证的成果（数据库层、IPC 层、UI 层往往各一次）。

### 3.2 提交信息一律英文

> 原话：「后续所有提交日志全部写英文」

用 Conventional Commits 格式：`feat(ui):` / `fix(ui):` / `refactor(ipc):` / `docs:` / `chore:` / `test:`。scope 用英文模块名。**中文只出现在代码注释与界面文案里，不出现在 commit message 里。**

### 3.3 提交后直接 push，不要再问

> 原话：「好的以后每次有 commit 之后都直接 push」

仓库已装 `post-commit` hook 自动推送。**提交完就结束了，不需要询问是否推送**，也不需要手动 `git push`。

### 3.4 阶段性提交，不做定时自动提交

> 原话：「初始化版本库。按阶段性定期提交。」

按可验证的阶段切分提交（如「接入 SQLite + Drizzle 与 IPC 数据契约」「实现桌面界面并从本地库读取」各一次），而不是按时间间隔批量提交。

### 3.5 只 push 代码部分

> 原话：「只 push 代码部分」

本地截图、验证产物、数据库文件、个人资料一律不入库——用 `.gitignore` 排除，**并且不要只是忽略，要从索引与历史里剥离干净**。README 里要用的图放到 `docs/screenshots/` 单独入库。

### 3.6 发布到 GitHub 由你代办

> 原话：「我的电脑里有配置过 GitHub 的权限…创建版本库也由你来 直接帮我发布到 GitHub 上。」

仓库创建、`gh` 授权引导、远程配置、hook 安装都归你做，不需要用户手动敲命令——只有 `gh auth login --web` 这类必须由用户在浏览器里完成的步骤才请他操作。

## 四、文档与对外口径

### 4.1 进度口径两处同步

> 原话：「在我们的工作目录下放一下一个 TODO list…不是代码目录啊」「把这个 To Do List 也放到代码目录下的 README 里面…两处都要，后续如果进度有变更，两处都要更新」

**两处，缺一不可：**

| 位置 | 路径 | 性质 |
|---|---|---|
| 工作目录 TODO | `~/WorkBuddy/spaces/2026_11_27_20-26-33/TODO.md` | 完整版，**在会话工作目录，不在代码目录** |
| 仓库 README | `~/Works/jobpilot/README.md` 末尾「当前进展与未完成事项」 | 公开版 |

执行顺序：**改动前先读 TODO.md → 改完同步 README 对应章节**。清单口径是**只列缺口**，不重复已完成项。

### 4.2 公开仓库不暴露实现工具痕迹

> 原话：「这个代码库是 public 的…不要透露用什么工具实现的，就像一个传统项目那样就行，把涉及到什么 work body 这些东西的描述去掉」

- README **只写「怎么用 + 项目介绍」**，删掉提交约定、分层原则、目录约定等内部流程描述。
- 全库扫一遍，删除提及具体工具/协作方式的过程性痕迹。**注意区分误伤**：`anthropic` / `cursor` 这类是正常业务词（LLM 厂商 / 断点续爬），不能改。
- 文档要写成传统项目风格，不自引用「README 声称……」这类措辞。

### 4.3 截图的用法

> 原话：「在工作目录下生成一个文件夹，专门放截图，把主要页面截个图放进去」「放点截图到 readme 里面去」

- 工作目录下建 `screenshots/` 放本地验证截图（不入库）。
- README 用的图放 `docs/screenshots/`，入库。

### 4.4 开发期工具不进正式版

> 原话：「那个打开 SQL 调试的窗口 仅在开发模式显示」

调试入口用 `app.isPackaged` 之类的判据隔离，正式版不出现。

### 4.5 版本号单一来源

> 原话：「写一个 hook 软件内的版本号使用项目 package 简介里面的版本号…每次编译的时候或者开发模式启动的时候，自动从 package.json 里面拿版本号到配置文件，然后显示的版本号从配置文件中读取」

版本号**只从仓库根 `package.json` 来**，通过构建钩子写入生成文件，应用内读生成文件。不要在多处硬编码版本号。

## 五、数据与安全红线（不可协商）

### 5.1 不得擅自改动原始工作目录

用户的原始工作目录（如 `~/Works`）属于用户资产。**写入、覆盖、移动、重命名、删除、还原覆盖全部禁止**，除非当次对话里得到明确同意；需要写入时优先选 `/tmp` 等隔离目录。备份类工具只取其「读取源目录」的能力。

### 5.2 不得擅自"测试回滚"

**未经明确同意，不验证回滚/还原效果。**允许的只读检查：快照列表、差异比对、完整性校验。会产生落盘文件的还原、挂载、轮转操作必须先问——即使得到同意，**还原目标也绝不能指向原始工作目录**，只能指向临时目录，由用户自行比对取用。

### 5.3 个人敏感信息不入库

简历原件、含个人信息的文件不进 Git（用 `.gitignore` 排除并从历史剥离）。需要用它的内容，转成结构化种子数据入库即可。

### 5.4 密钥用系统级加密

渠道密码、SMTP 密码、API Key 一律 `safeStorage.encryptString`。**不要自己写 AES + 硬编码密钥**，那等于明文。

## 六、验证与交付标准

### 6.1 硬门槛

每次改动后必须通过：

```bash
pnpm typecheck && pnpm build
```

### 6.2 有 UI 改动必须实拍

不要只靠读代码判断对错。用离屏截图（`scripts/shot.cjs`）实拍，**逐页核对明暗两套主题、中英两套语言、两个窗口尺寸**（1440×900 与 1040×660）。中文正常不代表英文不溢出——英文长度差异是高频问题。

### 6.3 数据改动必须验库

改完数据库相关逻辑：查库确认数据真的落进去了，重启确认持久化了，重置确认能恢复种子。写操作后统一「写库 → bumpRevision → 回读当前页」三步，别让界面读到过期数据。

### 6.4 排查顺序

先看 SQL 日志窗口确认「数据有没有进库」，再查读模型拼装，最后才看 UI。绝大多数「界面不对」的问题出在前两步。

### 6.5 交付要说清改了什么

最终回复要包含：改了哪些具体文件、验证结果、遗留问题与下一步。不能只说「已完成」。

## 七、UI 与交互偏好

### 7.1 文字优先于模糊图标

> 原话：「加号应该换个图标，应该让人感知点了之后是到列表，或者直接换成"管理"两个字」

按钮的含义要**一眼可辨**。能用文字说清楚就别用含义宽泛的图标；「+」这类符号无法自解释，应当换成「管理」「新增」这类动词。

### 7.2 弹层方向要符合预期

> 原话：「左下角当前求职者点开之后弹出的悬浮窗打开的方向是朝下的，显示不全，改成朝上」

贴边浮层默认朝内容区一侧展开，且**必须完整可见**。

### 7.3 滚动模型

外壳固定、内容区滚动。整页型页面（概览/求职者）整页滚，表格型页面（岗位池/投递）只滚表格，设置页滚右栏。**窗口内任何内容都不能被裁掉而无法滚动到。**

### 7.4 主题默认跟随系统

主题切换按钮**点击直接切到相反状态**，不要下拉三选一；设置页保留「跟随系统 / 浅色 / 深色」三选一。窗口底色与标题栏按钮配色要跟随主题重绘。

### 7.5 多语言必须双写

新增文案同时加 `zh` 与 `en`，`zh.ts` 是唯一真源，`en.ts` 受类型约束，写错 key 编译期报错。中文/英文都要实拍核对布局。

### 7.6 表单按语义分区

配置项按语义分类，左侧分类菜单 + 右侧表单，切换分类不丢草稿。

## 八、输出风格

- **中文**，简洁，**结构化分段**（标题 / 列表 / 表格），要有技术深度但不铺陈。
- 结论先行，再给依据；不要用「我将会…」代替实际动作。
- 遇到判断题，给出你的推荐和理由，不要罗列一堆可能性却不落地。
- 不确定的事要明说，并说明打算怎么处理。
- 代码注释解释「**为什么**」而不是「做了什么」。

## 十、附：与用户级硬性规则的对应

以下两条不属于本项目，而是跨项目的通用红线，任何项目都适用：

1. **禁止未经同意改动原始工作目录**（`~/Works` 及任何用户原始目录）——写入/覆盖/移动/重命名/删除/还原全部禁止；需要写入先征得同意，优先 `/tmp` 等隔离目录。
2. **禁止擅自"测试回滚"**——未获明确同意不验证还原效果；只读检查（快照列表 / 差异 / 完整性校验）可以，会落盘的还原操作必须先问；还原目标绝不能指向原始工作目录。

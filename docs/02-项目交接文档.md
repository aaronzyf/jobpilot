## 一、项目定位与核心设计

### 1.1 要解决的问题

一个人投简历时，岗位信息散在多个招聘平台，投递记录散在邮箱和表格里，面试邀约散在聊天窗口。这个应用把这些收进一处，并且**所有数据留在本机**（隐私卖点，也是简历文件不入云的前提）。

### 1.2 非账号体系

多个求职者共用一个应用，不是多人 SaaS。「切换求职者」= 换一份简历档案，岗位池全局共享（R6），匹配结果按人分存（R5）。这是整个数据模型的地基。

### 1.3 五个关键设计判断（摘自架构文档，务必先读）

1. **岗位池与匹配结果必须分表**。岗位是客观事实全局一份，匹配是主观判断按人各存一份。这样 JD 的 LLM 结构化解析只做一次，N 个求职者共享，成本不乘 N。
2. **渠道抽象只负责「获取」，投递单独抽象**。`JobSource` 管登录/取列表/取详情；`Submitter` 按投递通道（邮件 / ATS 表单 / 站内消息 / 手动）划分，与渠道解耦。
3. **登录用可辨识联合，不用可选方法**。`AuthRequirement` 是 `{kind:'none'} | {kind:'credentials'} | {kind:'qrcode'} | {kind:'browser-manual'}`，`'none'` 是显式合法状态，不是「不实现该方法」。
4. **匹配分档结果是「标记」不是「删除」**。`verdict: auto | confirm | reject` 三档都入库，调阈值后旧岗位能立刻重新出现，不需重跑。
5. **浏览器自动化放独立子进程**。用 `utilityProcess.fork()` 而不是 `child_process`——Playwright 会阻塞事件循环，且 Electron 打包成 asar 后目录扫描会失效（注册渠道必须用显式静态数组）。

## 三、技术架构

### 3.1 进程模型

```
┌─ Renderer (React 19) ─────────────────────────────────┐
│  Dashboard / 岗位池 / 投递 / 沟通 / 面试 / 求职者 / 设置     │
│  组件 → store(AppState) → services/db.ts → ipc.ts       │
└───────────────────────┬────────────────────────────────┘
                        │ contextBridge（仅 invoke / send / on）
┌───────────────────────▼────────────────────────────────┐
│ Main (Node)                                              │
│  ipc/registry.ts   类型化注册入口，无裸 ipcMain            │
│  db/service.ts     通道校验 + 委派 service                │
│  db/services/      用例编排（写→bumpRevision→回读）        │
│  db/repositories/  纯 SQL                                  │
│  db/mappers/       行 → View                               │
│  matching/engine.ts 后台调度（30s 一轮）                    │
│  db/sqlLog.ts      Drizzle logger 回调 → 环形缓冲           │
└──────────────────────────────────────────────────────────┘
                        │ (计划中：utilityProcess + Playwright)
┌───────────────────────▼────────────────────────────────┐
│ Worker (Playwright) —— 未实现                            │
└──────────────────────────────────────────────────────────┘
```

### 3.2 分层铁律

**数据读取层 → Service 业务层 → UI 层逐级调用，渲染进程只通过统一 IPC 入口。**

| 层 | 目录 | 职责 | 禁止 |
|---|---|---|---|
| Repository | `main/db/repositories/` | 只写 SQL，返回数据库行 | 不含业务规则、不组装 View、不决定版本号 |
| Mapper | `main/db/mappers/` | 纯函数，行 → View | 不查库、不写库 |
| Service | `main/db/services/` | 编排：取哪几组仓储数据、按什么顺序拼 | 不写 SQL |
| IPC 契约 | `packages/core/src/ipc/contract.ts` | 通道名 → 参数 → 返回，三张表钉死 | — |
| preload | `main/../preload/index.ts` | 只暴露 `invoke` / `send` / `on` | 不认识任何业务通道 |
| renderer service | `renderer/src/services/` | 把 IPC 包成业务函数 | 不直接拼通道名 |
| store | `renderer/src/lib/store.tsx` | 自研 Context store（**非** Zustand/Query） | — |
| UI | `renderer/src/pages/`、`components/` | 只消费 store 的字段 | 不直接调 ipc（除设置页取 `app:info`） |

改一个通道必须三处同步（契约 / 主进程注册 / 渲染层调用），漏改任何一处 `tsc` 就会报错——这是刻意的设计。

### 3.3 数据流：按页读 + 写后回读

读：`db:load` 携带 `ViewQuery{ page, candidateId, jobs?, ... }` → `readView()` 按页只查当前页用得到的那几组数据 → 返回 `LoadResult{ sidebar, view }`。

写：任何写操作统一走 `after(handle, query, mutate)` 三步——**写库 → `bumpRevision` → 回读当前页**，界面整体替换内存状态。好处是侧栏角标、指标卡、图表这类派生值永远与库一致；代价是每次写都重算一遍读模型（当前数据量可忽略，表大了要改成按 key 失效的增量刷新）。

「点开才读」的详情不进页面默认切片：`db:load-resume` 单独返回 `ResumeView`，避免每个页面都拖着全量简历正文走。

### 3.4 读模型与写模型分离

表是写模型（列拆细、无冗余），页面要的是 `packages/core/src/domain/view.ts` 里的 `*View`（时间已是 ISO 字符串、统计已聚合、匹配按求职者分好组）。转换在主进程完成，渲染层不碰数据库行。

三条贯穿全局的取舍：

1. **能派生的都不存**。候选人的 `applied / replied / pending / interview`、会话未读数、保存视图命中数、概览页全部图表，都是从明细表现算。冗余列只在排序这种高频路径上保留（`conversations.last_message_at`）。
2. **时间只存毫秒时间戳**。不存「2 小时前」这类与语言、此刻绑定的文案；仓储层转 ISO，渲染层用 `Intl` 按当前语言格式化。
3. **读模型单独定义**（见上）。

### 3.5 领域层（`packages/core`，零 Electron 依赖）

- `domain/types.ts`：枚举与领域接口。含 `Verdict`、`ApplicationStatus`、`InterviewStatus`、`CommStage`、`SubmitChannel`，以及 `CandidateProfilePatch`（档案配置补丁）、`ResumeEntryKind` / `ResumeContact` / `ResumeSkillGroup`（简历正文类型）。
- `domain/view.ts`：全部读模型 + `ViewQuery` / `ViewSnapshot` / `SidebarSnapshot` / `LoadResult`。
- `source/types.ts`：渠道抽象。`JobSource`（meta + auth + 可选的 list/detail/apply + 必填 normalizer）、`ListProvider` / `DetailProvider` / `ApplyProvider` / `JobNormalizer`、`SourceContext`、`ListQuery`、`RawJobDetail`，以及 `assertSourceContract()`——**启动时自检「声明了能力但没实现」，把运行时静默失败提前到启动期显式报错**。
- `ipc/contract.ts`：`InvokeContract` / `SendContract` / `EventContract` 三张表。

### 3.6 IPC 通道全表

**Invoke（请求-响应）**

| 通道 | 作用 |
|---|---|
| `app:info` | 版本、平台、数据目录 |
| `db:snapshot` | 一次读全（脚本 / 旧调用方用） |
| `db:load` | 按页读 `ViewQuery` → `LoadResult` |
| `db:load-resume` | 读某位求职者的简历预览 → `ResumeView \| null` |
| `db:mark-conversation-read` / `db:mark-all-read` | 会话已读 |
| `db:send-message` | 追加一条 `dir='out'` 消息 |
| `db:set-interview-status` | 面试邀约状态流转 |
| `db:set-job-saved` | 岗位收藏 |
| `db:set-application-status` | 投递状态流转 |
| `db:set-active-candidate` | 切换当前求职者 |
| `db:set-candidate-enabled` | 档案启用/禁用（当前档案拒绝禁用） |
| `db:set-candidate-profile` | 保存档案配置（资料/阈值/邮箱/SMTP/POP3/日上限） |
| `db:reset` | 清空业务表 + 重灌种子 |
| `sql-log:list` / `status` / `clear` / `set-enabled` | SQL 日志窗口 |

**Send（单向）**：`theme:set-mode`、`sql-log:open`
**Event（主→渲染）**：`sql-log:entry`、`sql-log:cleared`、`match:run`

## 四、数据模型

17 张表（`src/apps/desktop/src/main/db/schema.ts`），4 个迁移版本。

| 表 | 职责 | 关键点 |
|---|---|---|
| `candidates` | 求职者档案、阈值、SMTP/POP3、简历元信息 | `stats` 不入库；`enabled` 控制后台调度 |
| `resume_documents` | 简历正文主体 | 简介 / 求职意向 / 技能分组 / 联系方式，JSON 列 |
| `resume_items` | 简历时间线条目 | `kind` = experience / project / education，`position` 保序 |
| `sources` | 渠道配置与运行状态 | `capabilities` 存 JSON |
| `jobs` | 岗位池，全局共享（R6） | `posted_at` 与 `discovered_at` 分开；`UNIQUE(source_id, external_id)` 防重复 |
| `job_scores` | 岗位 × 求职者的分数、判定、理由、缺口 | 复合主键 `(job_id, candidate_id)` |
| `match_runs` | 后台扫描摘要 | 每个档案每轮的扫描量与新增量 |
| `job_bookmarks` | 收藏 | 与打分解耦 |
| `applications` | 投递记录与邮件正文 | `submitted_at` 真实时间戳 |
| `application_logs` | 投递过程留痕 | `seq` 保序 |
| `conversations` | 会话（R12） | `last_message_at` 冗余排序键 |
| `messages` | 消息 | **未读数不落库** |
| `interviews` | 面试邀约（R13） | 结束时间由 `starts_at + duration_min` 推出 |
| `interview_interviewers` | 面试官 | 一对多 |
| `saved_views` | 岗位池保存视图 | 条件存 JSON，命中数现算 |
| `llm_usage` | 大模型调用汇总 | 金额按分存，避免浮点；**缺 `llm_calls` 明细表** |
| `settings` | 应用级 KV | `active_candidate_id`、`revision` |

**迁移机制**：不用 drizzle 官方 migrator（它要求 migrations 目录在磁盘上存在，而这里是内联的），自己跑：建 `_migrations` 表记已执行版本，pending 的整批包在一个事务里执行。SQL 里用 `--> statement-breakpoint` 分隔语句。

**PRAGMA**（`db/index.ts`）：`journal_mode = WAL`、`synchronous = NORMAL`、**`foreign_keys = ON`（SQLite 默认不校验外键，必须每连接打开）**。

## 八、待办需求：大模型设置双模式（**尚未实现，需求方已明确提出**）

> 需求原文：「设置里面的大模型设置，分两种情况，一种是使用内置的，也就是我们自己服务端提供的，另外一种是用户自己配置的。」

### 8.1 语义

当前设置页「模型」分区只有单一形态：4 张供应商卡片（DeepSeek / Anthropic / OpenAI / Ollama）+ 一个 API Key 输入框 + 4 个场景模型下拉（JD 解析 / 匹配 / 求职信 / 字段抽取）+ 用量表。全部只改本地 state，**不落库、不校验**。

需要改成**两种模式二选一**：

| 模式 | 含义 | 用户要填什么 | 我们要做什么 |
|---|---|---|---|
| **内置服务**（built-in） | 由我们自己的服务端代理转发大模型调用 | 什么都不用填（或只选模型） | 应用调用我们的服务端网关，由网关持有各供应商 Key、做配额/计费/审计 |
| **自带 Key**（byo-key） | 用户填自己的 API Key，直连供应商 | API Key、Base URL（可选）、模型 | 密钥加密落库（`safeStorage`），直连调用 |

### 8.2 建议的数据模型

现成的 `llm_configs` 表**只存在于架构文档里，尚未在 `schema.ts` 落地**。建议直接按两种模式扩展：

```ts
export const llmConfigs = sqliteTable('llm_configs', {
  id: text('id').primaryKey(),
  // built-in：由我们的服务端代理，用户无需提供密钥
  // byo-key：用户自带密钥
  mode: text('mode').$type<'built-in' | 'byo-key'>().notNull(),
  provider: text('provider').notNull(),          // openai / anthropic / deepseek / ollama / built-in
  baseUrl: text('base_url'),
  model: text('model').notNull(),
  // byo-key 才有值；built-in 模式下这里存服务端下发的短期令牌或为空
  apiKeyEnc: blob('api_key_enc'),
  purpose: text('purpose').notNull(),            // parse / match / cover-letter / extract，可分场景配不同模型
  isDefault: integer('is_default').notNull().default(0),
  createdAt: integer('created_at', { mode: 'timestamp_ms' }).notNull(),
  updatedAt: integer('updated_at', { mode: 'timestamp_ms' }).notNull()
})
```

密钥一律 `safeStorage.encryptString`（macOS 钥匙串 / Windows DPAPI）——**不要自己写 AES + 硬编码密钥，那等于明文**。

### 8.3 建议的实现顺序

1. **先落库 + 持久化**（不接网关）：把当前设置页的 provider / API Key / 场景模型改为落 `llm_configs`，加 `mode` 字段。这一步独立可验收，顺带解决 7.2 里的「设置页不落库」。
2. **再落 UI 的模式切换**：设置页顶部加「内置服务 / 自带 Key」切换；内置模式下隐藏 API Key 输入框，自带 Key 模式下显示并提供「测试连接」（真实发起一次最小请求，校验 baseUrl + key + model）。
3. **最后接网关**：新增 `packages/llm`，定义统一调用接口，两种模式各一个实现：
   - `built-in`：请求打到我们的服务端（URL + 鉴权方式待定，需要产品决策）。
   - `byo-key`：直连供应商（OpenAI 兼容协议可统一；Anthropic 需单独适配）。
   - `packages/core` 不依赖任何 Electron 或网络细节，接口放这里，测试放 `packages/core` 里。
4. **接入调用方**：把 `main/matching/engine.ts` 的 `heuristic-v1` 启发式换成 LLM 打分（这是 R3 的真正目的），并把 JD 结构化解析、求职信生成接上。

### 8.4 待产品决策

- 内置服务的网关地址、鉴权方式、是否需要用户登录/配额？
- 内置模式下用户还能不能覆盖某个场景的模型？
- 两种模式能否共存（比如 JD 解析走内置、求职信走自带 Key）？**建议允许**——`llm_configs.purpose` 字段本来就是为分场景设计的。
- 失败降级策略：内置服务不可用时，是报错还是回退到自带 Key？

## 十、已知坑（都是踩过的，别再踩一遍）

1. **浮层被页面内容盖住 / 被裁切**：`.page-enter > *` 的 `transform` 动画会创建新的 containing block，弹窗里的 `fixed` 元素改以页面容器为参照。**必须 `createPortal` 到 `document.body`**（`components/ui/overlay.tsx` 已有 `Portal`，`Dialog`/`Sheet` 都包了）。
2. **tsx / node 跑不了主进程代码**：`?raw` 导入、路径别名、`import { type X }` 内联类型都过不了。验证主进程逻辑要用 **esbuild 打包**：`--bundle --platform=node --format=cjs --loader:.sql=text --external:electron --external:better-sqlite3 --external:drizzle-orm --alias:@core=./src/packages/core/src/index.ts`，产物用完即删。
3. **`exec` 里的双引号被当成标识符**：`sqlite.exec('... "c1" ...')` 会报 `no such column: "c1"`。写临时脚本时用 `prepare().run(?)` 参数绑定。
4. **SQLite 不开外键等于没有外键**：必须每连接 `pragma('foreign_keys = ON')`。
5. **Electron 脚本要用 Electron 跑，不是 node**：`scripts/shots.cjs` / `scripts/shot.cjs` / `scripts/db-reset.cjs` 需要 `require` 打包后的主进程。本机 shell 自带 `ELECTRON_RUN_AS_NODE=1`，要先 unset：
   ```bash
   env -u ELECTRON_RUN_AS_NODE ./node_modules/.bin/electron scripts/shots.cjs 1440 900
   ```
6. **新增迁移要改两处**：`db:generate` 生成 SQL 后，还要在 `src/main/db/migrations.ts` 的 `migrations` 数组末尾追加 `{ id, sql }`。
7. **渠道注册必须用显式静态数组**，不能扫描目录动态加载——Electron 打包成 asar 后目录扫描会失效。
8. **better-sqlite3 13 起不需要 electron-rebuild**，但打包时要配 `asarUnpack`（`.node` 文件不能从 asar 里加载）。
9. **不要用 `rm -rf` 处理个人目录**。本项目内 `~/Works` 属于用户的原始工作目录，改动前先确认；备份类操作只读取源目录。

## 二、五个核心设计判断

### 1. 岗位池与匹配结果必须分表（R5 + R6）

这是整个数据模型的地基。岗位是客观事实，全平台共享一份；匹配是主观判断，按求职者各存一份。

好处不只是"不重复拉取"。更重要的是：**JD 的结构化解析（用 LLM 提取技能、年限、薪资、联系方式、邮件主题规则）只需要做一次**，之后 N 个求职者共享这份解析结果。如果按求职者存岗位，同样一条 JD 会被 LLM 解析 N 遍，成本直接乘以 N。

分表之后，成本模型是：`渠道数 × 岗位数 × 1 次解析 + 岗位数 × 求职者数 × 1 次打分`。打分比解析便宜得多（可以用小模型或向量预筛）。

### 2. 渠道抽象只负责"获取"，投递单独抽象（R1 + R8）

需求里说渠道 interface 要包含"怎么登录、取列表、取详情"，这三件事都是**获取**。但投递不是——同一个渠道上的不同岗位，投递方式可能完全不同：有的站内发消息，有的要求发邮件到指定邮箱，有的跳转官网表单。

所以拆成两个抽象：

- `JobSource`：一个渠道一个，负责登录态和取数据。
- `Submitter`：按**投递通道**划分，与渠道解耦。因为邮件投递可能来自任何一个渠道的 JD。

这样「在 BOSS 上看到一个岗位，但它要求发邮件到 hr@xx.com」这种最常见的情况才不会写死在渠道里。

### 3. 登录用可辨识联合，而不是可选方法（R1）

需求里特别提到"是否需要登录"。不要设计成 `login?(): Promise<void>` 这种可选方法——那样每个实现都要判断自己该不该实现，调用方也要到处判空。

用 TypeScript 的可辨识联合，把"不需要登录"变成一个**显式的合法状态**：

```ts
type AuthRequirement =
  | { kind: 'none' }
  | { kind: 'credentials'; ... }
  | { kind: 'qrcode'; ... }
  | { kind: 'browser-manual'; ... }
```

新增一个不需要登录的渠道（比如公开的 RSS、公司官网列表页）时，只需写 `auth: { kind: 'none' }`，一行代码，不实现任何登录方法。

### 4. 匹配分档结果是"标记"，不是"删除"（R4）

三档对应 `verdict: 'auto' | 'confirm' | 'reject'`，三种都写进 `matches` 表。"完全不匹配"只是 UI 上分到另一个列表，数据不丢。因为阈值是可调的——用户把阈值从 80 调到 60，昨天被判 reject 的岗位要能立刻重新出现，而不能需要重跑一遍。

### 5. 浏览器自动化放独立子进程（R1）

用 Electron 的 `utilityProcess.fork()` 而不是 `child_process`。理由：
- Playwright 会阻塞事件循环，放主进程会让 UI 卡死
- 浏览器崩溃不拖垮应用
- 可以用 Playwright 自带的 Chromium，UA 和指纹比 Electron 内置内核更接近真实浏览器

## 四、渠道抽象（R1 核心）

### 4.1 拆分原则

按「一件事一个接口」组织，用**组合**拼装出渠道，而不是一个大接口配一堆 `throw new Error('not implemented')`。

大接口的问题是：声明了十种能力、实现了三种，剩下七种要留空壳，空壳会在运行时才炸。拆成能力接口之后，「没有这个能力」变成类型层面就成立的事实——渠道对象上根本没有这个属性，调用方也就无从误用。

### 4.2 类型定义

  config: SourceConfig
  logger: Logger

/* ---------- 能力接口：一个接口只描述一件事 ---------- */

/** R1: 取列表。异步迭代器，天然支持分页与断点续爬 */
export interface ListProvider {
  fetchList(ctx: SourceContext, query: ListQuery): AsyncIterable<RawJobSummary>

/** R1: 取详情。JD 全文、联系方式、投递线索 */
export interface DetailProvider {
  fetchDetail(ctx: SourceContext, ref: JobRef): Promise<RawJobDetail>

export interface JobNormalizer {
  normalize(raw: RawJobSummary | RawJobDetail): NormalizedJob
}

/** 站内投递能力。只有站内沟通型渠道才实现这个接口 */
export interface ApplyProvider {
  apply(ctx: SourceContext, req: ApplyRequest): Promise<ApplyResult>
}

/* ---------- 用组合拼出渠道，而不是一个大接口 ---------- */

export interface JobSource {
  readonly meta: SourceMeta
  readonly auth: AuthRequirement

  readonly list?: ListProvider        // 可选：没有列表能力的渠道（如单页爬取）就不实现
  readonly detail?: DetailProvider    // 可选：列表里已含全文的渠道可以省掉
  readonly normalizer: JobNormalizer  // 必填：只要能产出数据就必须能归一化
  readonly apply?: ApplyProvider      // 可选：仅站内沟通型渠道实现
}

### 4.3 声明与实现的一致性自检

`meta.capabilities` 是给 UI 和调度器看的声明，能力接口是真实实现。两者必须对得上，否则会退化成"声明了但一调就崩"。启动时校验一次：

```ts
export function assertSourceContract(s: JobSource): void {
  const c = s.meta.capabilities
  const missing: string[] = []
  if (c.list && !s.list) missing.push('list')
  if (c.detail && !s.detail) missing.push('detail')
  if (c.apply !== 'none' && !s.apply) missing.push('apply')
  if (missing.length) {
    throw new Error(`[${s.meta.id}] 声明了能力但未实现: ${missing.join(', ')}`)
  }
}
```

这才是拆接口的实际收益：把「能力没实现」从**运行时静默失败**提前到**启动期显式报错**。

### 4.4 新增一个渠道的成本

```
1. 建目录 src/main/sources/<id>/
2. 实现 index.ts，导出 const source: JobSource = { ... }
3. 在 src/main/sources/registry.ts 的数组里加一行
```

**不需要改动**：调度器、匹配流水线、投递器、数据库、任何 UI。配置界面会自动根据 `meta` 和 `auth.fields` 渲染。

> 注意：注册必须用**显式的静态数组**，不能扫描目录动态加载。Electron 打包成 asar 后目录扫描会失效，这是必须提前避开的坑。

## 五、数据模型（SQLite）

```sql
-- ========== 求职者（R5，非账号体系） ==========
CREATE TABLE candidates (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  note          TEXT,                        -- R9 的自然语言配置
  created_at    INTEGER NOT NULL
);

-- ========== 简历 ==========
CREATE TABLE resumes (
  id            TEXT PRIMARY KEY,
  candidate_id  TEXT NOT NULL REFERENCES candidates(id) ON DELETE CASCADE,
  file_path     TEXT NOT NULL,               -- 原始上传文件
  file_hash     TEXT NOT NULL,
  parsed_json   TEXT,                        -- 结构化解析结果
  is_primary    INTEGER NOT NULL DEFAULT 1,
  created_at    INTEGER NOT NULL
);

-- 投递时绑定的简历快照，防止后续改简历影响历史记录
CREATE TABLE resume_snapshots (
  id            TEXT PRIMARY KEY,
  resume_id     TEXT NOT NULL REFERENCES resumes(id),
  pdf_path      TEXT NOT NULL,
  pdf_hash      TEXT NOT NULL,
  content_json  TEXT NOT NULL,               -- 当次渲染出的完整内容
  created_at    INTEGER NOT NULL
);

-- ========== 渠道配置（R7） ==========
CREATE TABLE source_configs (
  source_id          TEXT PRIMARY KEY,
  enabled            INTEGER NOT NULL DEFAULT 1,
  credentials_enc    BLOB,                   -- safeStorage 加密
  refresh_interval   INTEGER NOT NULL,       -- 分钟
  last_run_at        INTEGER,
  cursor             TEXT,                   -- 断点续爬
  settings_json      TEXT
);

-- ========== 岗位池（R6，全局共享） ==========
CREATE TABLE jobs (
  id                TEXT PRIMARY KEY,
  source_id         TEXT NOT NULL,
  external_id       TEXT NOT NULL,
  company           TEXT NOT NULL,
  title             TEXT NOT NULL,
  city              TEXT,
  country           TEXT,
  remote_type       TEXT,                    -- remote / hybrid / onsite
  employment_type   TEXT,                    -- fulltime / parttime / intern / contract
  salary_min        INTEGER,
  salary_max        INTEGER,
  salary_currency   TEXT,
  description       TEXT,                    -- JD 全文
  -- 以下由 LLM 一次性解析，全员共享
  parsed_json       TEXT,                    -- 技能、年限、学历、加分项
  email_subject_rule TEXT,                   -- R8: JD 约定的主题格式
  contact_emails    TEXT,                    -- JSON 数组
  external_url      TEXT,
  -- 投递通道判定
  submit_channel    TEXT,                    -- email / ats-form / platform-message / manual
  posted_at         INTEGER,
  first_seen_at     INTEGER NOT NULL,
  last_seen_at      INTEGER NOT NULL,
  detail_fetched_at INTEGER,
  raw_json          TEXT,
  UNIQUE (source_id, external_id)            -- 唯一约束，防重复入库
);

CREATE INDEX idx_jobs_first_seen ON jobs(first_seen_at);
CREATE INDEX idx_jobs_channel    ON jobs(submit_channel);

-- ========== 匹配结果（按求职者，R4 + R5） ==========
CREATE TABLE matches (
  id            TEXT PRIMARY KEY,
  job_id        TEXT NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
  candidate_id  TEXT NOT NULL REFERENCES candidates(id) ON DELETE CASCADE,
  score         INTEGER NOT NULL,            -- 0-100
  verdict       TEXT NOT NULL,               -- auto / confirm / reject  R4 三档
  dimensions    TEXT,                        -- JSON: 技能/经验/薪资/地点 分项
  reason        TEXT,                        -- 给用户看的理由
  model         TEXT,
  created_at    INTEGER NOT NULL,
  UNIQUE (job_id, candidate_id)
);

CREATE INDEX idx_matches_verdict ON matches(candidate_id, verdict, score DESC);

-- ========== 投递记录（幂等 + 留痕） ==========
CREATE TABLE applications (
  id                TEXT PRIMARY KEY,
  job_id            TEXT NOT NULL REFERENCES jobs(id),
  candidate_id      TEXT NOT NULL REFERENCES candidates(id),
  resume_snapshot_id TEXT NOT NULL REFERENCES resume_snapshots(id),
  submit_channel    TEXT NOT NULL,
  status            TEXT NOT NULL,           -- draft/pending_confirm/queued/sent/failed/replied/rejected
  cover_letter      TEXT,
  email_to          TEXT,
  email_subject     TEXT,
  email_body        TEXT,
  evidence_path     TEXT,                    -- 截图或回执
  error             TEXT,
  created_at        INTEGER NOT NULL,
  sent_at           INTEGER,
  UNIQUE (job_id, candidate_id)              -- R4: 同一岗位对同一人只投一次
);

-- ========== 邮箱账号（R8，按简历配置） ==========
CREATE TABLE email_accounts (
  id            TEXT PRIMARY KEY,
  candidate_id  TEXT NOT NULL REFERENCES candidates(id) ON DELETE CASCADE,
  smtp_host     TEXT NOT NULL,
  smtp_port     INTEGER NOT NULL,
  smtp_secure   INTEGER NOT NULL,
  username      TEXT NOT NULL,
  password_enc  BLOB NOT NULL,               -- safeStorage 加密
  from_name     TEXT,
  verified_at   INTEGER
);

-- ========== 大模型配置（R3） ==========
CREATE TABLE llm_configs (
  id            TEXT PRIMARY KEY,
  provider      TEXT NOT NULL,               -- openai / anthropic / deepseek / ollama
  base_url      TEXT,
  model         TEXT NOT NULL,
  api_key_enc   BLOB,
  purpose       TEXT NOT NULL,               -- parse / match / cover-letter（可分场景用不同模型）
  is_default    INTEGER NOT NULL DEFAULT 0
);

-- ========== 阈值等全局设置 ==========
CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- match.auto_threshold    默认 85
-- match.reject_threshold  默认 40
```

### 5.1 已落地的表结构（v0.2）

上面的草案是设计意图，实际实现按「先能跑起来、再补简历/LLM 配置」的顺序收敛成了 14 张表。
schema 在 `src/apps/desktop/src/main/db/schema.ts`（Drizzle），迁移 SQL 由 `drizzle-kit generate` 产出。

| 表 | 职责 | 关键点 |
|---|---|---|
| `candidates` | 求职者档案、阈值、SMTP、简历元信息 | `stats` 不入库 |
| `sources` | 渠道配置与运行状态 | `capabilities` 存 JSON，能力声明与实现的对齐由适配器自检 |
| `jobs` | 岗位池，全局共享（R6） | `posted_at` 与 `discovered_at` 分开 |
| `job_scores` | 岗位 × 求职者的分数、判定、理由、缺口 | 复合主键 `(job_id, candidate_id)` |
| `job_bookmarks` | 收藏 | 与打分解耦 |
| `applications` | 投递记录与邮件正文 | `submitted_at` 是真实时间戳 |
| `application_logs` | 投递过程留痕 | `seq` 保序 |
| `conversations` | 会话（R12） | `last_message_at` 是冗余排序键 |
| `messages` | 消息 | **未读数不落库** |
| `interviews` | 面试邀约（R13） | 结束时间由 `starts_at + duration_min` 推出 |
| `interview_interviewers` | 面试官 | 一对多 |
| `saved_views` | 岗位池保存视图 | 条件存 JSON，命中数现算 |
| `llm_usage` | 大模型调用汇总 | 金额按分存，避免浮点 |
| `settings` | 应用级 KV | 当前求职者、自动化档位、数据 revision |

三条贯穿全局的取舍：

1. **能派生的都不存。** 候选人的 `applied / replied / pending / interview`、会话未读数、
   保存视图命中数、概览页全部图表，都是从明细表现算。冗余列只在排序这种高频路径上保留
   （`conversations.last_message_at`）。
2. **时间只存毫秒时间戳。** 不存「2 小时前」「今天 09:42」这类文案——它们与语言、与此刻绑定。
   仓储层读出来转 ISO，渲染层再用 `Intl` 按当前语言格式化。
3. **读模型单独定义。** 表是写模型（列拆细、无冗余），页面要的是 `@core` 里的 `*View`
   （时间已是 ISO、统计已聚合、匹配按求职者分好组）。转换在主进程完成，渲染层不碰数据库行。

迁移的执行方式也做了一点非主流选择：不读 migrations 目录，而是用 `?raw` 把 SQL 内联进主进程包，
用 `_migrations` 表记录已执行版本。好处是打包后不依赖 asar 外的资源路径，坏处是新增迁移要手动
在 `src/main/db/migrations.ts` 里追加一行。

种子数据来自原来渲染层的 `mock.ts`，首次启动（`candidates` 为空）时写入，时间按「相对此刻」生成。
`scripts/db-reset.cjs` 可以清库重灌。

数据库落在 `app.getPath('userData')/jobpilot.db`（macOS 为
`~/Library/Application Support/jobpilot/jobpilot.db`）。应用启动时 `initDatabase()` 建表、
按 `_migrations` 记录的版本执行迁移，只有 `candidates` 为空才灌种子——已有数据不会被覆盖。
三个辅助脚本必须用 Electron 而不是 `node` 运行（它们要 `require` 打包后的主进程才能拿到
`window.jobpilot`；本机 shell 自带 `ELECTRON_RUN_AS_NODE=1`，需先 unset）：

```
env -u ELECTRON_RUN_AS_NODE ./node_modules/.bin/electron scripts/shots.cjs 1440 900
```

**IPC 契约。** `preload` 暴露 `window.jobpilot.db`：一次全量读 + 8 个写通道，全部在主进程
注册，渲染层不碰 SQL、也不持有连接。

| 通道 | 作用 |
|---|---|
| `db:snapshot` | 首屏拉完整 `AppSnapshot`（读模型，见 5.1 第 3 条） |
| `db:mark-conversation-read` / `db:mark-all-read` | 给 `dir='in'` 且 `read_at IS NULL` 的消息打上已读时间 |
| `db:send-message` | 追加一条 `dir='out'` 消息，顺带更新会话的 `last_message_at` |
| `db:set-interview-status` | 邀约状态（接受 / 改期 / 拒绝 …） |
| `db:set-job-saved` | 收藏 |
| `db:set-application-status` | 投递状态流转 |
| `db:set-active-candidate` | 当前求职者 |
| `db:reset` | 清空业务表 + 重灌种子 |

写操作统一「先落库、再回传一份新快照」，`AppProvider` 拿到后整体替换内存状态。这样侧栏徽章、
指标卡、图表这些派生值永远与库一致，不用在每个页面里手动同步；代价是每次写都要重算一遍读模型，
当前数据量下可忽略，后续表大了可以改成按 key 失效的增量刷新。

**设置页的数据分区**同时接上了真实数据：文件路径由 `app:info` 返回，数据量现数
`jobs` / `applications`，「重置示例数据」直接调 `db:reset`，便于反复验证界面。

### 5.3 SQL 日志窗口（调试）

`src/main/db/sqlLog.ts` 挂到 Drizzle 的 `logger` 回调上，采集 query + params 存进 500 条环形缓冲；**没有窗口时也在采**，所以打开日志窗口能看到此前的查询。主进程注册 `sql-log:*` IPC，新条目通过 `webContents.send` 推给已打开的窗口，窗口关闭即退订。

日志窗口是第二个 renderer 入口 `sqllog.html`，与主界面共用 preload 和主题令牌；`electron.vite.config.ts` 里用 `rollupOptions.input` 配双入口。界面提供文本过滤、暂停/继续、清空、自动滚动和点击复制。

采集只覆盖经 Drizzle 的查询——迁移走原生 `exec`，不进日志。参数统一在主进程序列化成字符串再过 IPC，避免不可序列化的值。

## 六、匹配与分档流水线（R2 + R4）

```
拉取列表 ──► 入库去重(UNIQUE) ──► 拉详情 ──► JD 结构化解析【全局一次】
                                                      │
                    ┌─────────────────────────────────┤
                    ▼                                 ▼
          求职者 A 打分                    求职者 B 打分    【每人一次】
                    │                                 │
                    ▼                                 ▼
            score ≥ auto_threshold  ──────► verdict = auto     → 自动投递
            reject_threshold ≤ score < auto ─► verdict = confirm → 待人工确认列表
            score < reject_threshold ─────► verdict = reject   → 未匹配列表（单独 tab）
```

打分输入 = `parsed_json` + 简历 `parsed_json` + 该求职者的 `note`（R9）。

为了控制成本，打分分两段：
1. **粗筛**：技能关键词命中率 + 年限 + 地点 + 薪资，纯本地计算，无 LLM 成本，先淘汰明显不合适的
2. **精排**：对通过粗筛的岗位调 LLM，输出分数、分项、理由

粗筛能挡掉大部分，LLM 调用量会降一个数量级。

## 七、投递链路（R8）

### 7.1 邮件投递的五个步骤

```
1. 取数据    job.contact_emails + job.email_subject_rule（JD 解析时已提取）
2. 写求职信  LLM 生成，输入 = JD + 简历 + 求职者 note，输出需过事实校验
3. 渲染主题  有 rule → 按 rule 生成；无 rule → 默认「应聘{岗位}-{姓名}-{年限}」
4. 校验主题  检查是否包含 rule 要求的片段、长度是否超限 → 不通过则报错而非静默发送
5. 预览确认  auto 档可跳过人工确认但仍落库；confirm 档必须人工过目
             ──► nodemailer 发送 ──► 存 messageId 与回执
```

主题规则的两种来源要分开处理：
- **JD 里明确写了格式**（"邮件主题请注明：姓名+岗位+工作年限"）→ 严格按格式，缺字段就报错
- **JD 没写** → 用默认模板，不硬套

### 7.2 求职信的真实性约束

求职信和简历改写的风险不同——它更容易出现"我了解贵公司的 XX 业务"这类捏造。约束方式：
- 生成时只允许引用 `job.description` 中出现的事实和简历中存在的经历
- 输出后做一次交叉校验，出现 JD 和简历里都没有的专有名词就重新生成
- 生成结果与 `model` 一起落库，出问题可追溯

## 八、调度与限速（R7）

- 每个渠道独立计时，`next_run = last_run_at + refresh_interval`
- 启动时读 `last_run_at`，**不立刻全量拉取**——避免每次开软件都触发一轮抓取
- 全局令牌桶限制并发，单渠道同时只跑一个任务
- 失败退避：1min → 5min → 15min → 60min，连续失败 3 次则暂停该渠道并在 UI 上提示
- 断点续爬：`cursor` 存 DB，中断后从上次位置继续

## 九、安全与密钥

| 数据 | 处理方式 |
|---|---|
| 渠道账号密码 | `safeStorage.encryptString`，存 BLOB |
| SMTP 密码 | 同上 |
| LLM API Key | 同上 |
| 简历文件 | 存 `app.getPath('userData')/resumes/`，不进 git |
| 岗位数据 | 明文 SQLite，可公开内容 |

`safeStorage` 在 macOS 走钥匙串、Windows 走 DPAPI，是该平台上唯一的正确做法。**不要自己写 AES + 硬编码密钥**，那等于明文。

## 十一、技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 壳 | Electron + electron-vite | 官方推荐的构建方案，HMR 体验好 |
| UI | React + Tailwind + shadcn/ui | 表格和表单密集的界面，这套最快 |
| 状态 | TanStack Query + Zustand | 服务端状态与本地状态分离 |
| DB | SQLite + better-sqlite3 + Drizzle | 同步 API 适合主进程；Drizzle 类型推导好 |
| 校验 | Zod | IPC 边界和 LLM 输出都要校验 |
| 浏览器 | Playwright + utilityProcess | 独立进程，可用真实 Chromium |
| 邮件 | nodemailer | 成熟，支持附件与连接池 |
| 打包 | electron-builder | 双端 + 公证/签名的标准路径 |

> better-sqlite3 13 起改用 N-API + 预编译包（`prebuilds/darwin-arm64.node`、`win32-x64.node` 等随包发布），
> 不再需要 `electron-rebuild` 或按 ABI 重编，一份依赖同时适配 Node 与 Electron。实测在 Electron 45 中直接可用。
> 打包时仍需配 `asarUnpack`，因为 `.node` 文件不能从 asar 里加载。

## 十三、待确认的开放问题

1. **第一批要接哪几个渠道？** 建议 2 个（1 国内 + 1 海外），验证抽象层是否站得住。
2. **自动投递的日配额上限设多少？** 分档里 auto 档是真自动发送，需要护栏。
3. **是否需要收信能力（IMAP）？** 如果要追踪"HR 是否回复"，需要额外接 IMAP，工作量不小。
4. **自动阈值和淘汰阈值的默认值？** 方案里暂定 85 / 40。
5. **求职信是否要支持多语言？** 海外岗位需要英文求职信。
6. **面试邀约从哪来？** 平台同步能拿到结构化字段（时间、形式、面试官），邮件只能靠规则或大模型从正文里抽。要不要在 M2 一起把 IMAP 收信做了，顺带解决「HR 是否回复」的追踪？
